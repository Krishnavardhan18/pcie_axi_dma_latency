\chapter{Background}

\label{Chapter3}

\lhead{Chapter 3. \emph{Background}}

This chapter lays out the steps and technical details needed to support the latency model that will be used later on. It starts by going over the key points of the PCIe transaction layer, then moves on to the AMBA AXI4 and AXI4-Stream protocols. After that, it explains how descriptor-based DMA works, and finally, it puts all these pieces together to create the fixed-plus-proportional latency model that will be used throughout the rest of the thesis. This model is important because it helps us understand how different parts of the system work together to affect overall performance. By breaking down the technical details into smaller parts, we can get a better sense of how they fit into the bigger picture. The goal is to create a clear and accurate model that can be used to make predictions and guide decision-making.

\section{The PCIe Transaction Layer}
\label{sec:ch3_pcie}

PCIe is a way of connecting devices that uses a point-to-point, packet-switched system. It's made up of three main layers: the physical layer, the data link layer, and the transaction layer. When a device wants to read or write data, it sends a request through the transaction layer using something called a Transaction Layer Packet, or TLP for short. Each TLP has a header that includes important information like what type of transaction it is, who's requesting it, and where the data is supposed to go. The header is usually 12 or 16 bytes long, depending on how the device is addressed. The TLP also carries the actual data being sent, which is called the payload. There are two things in this system that can slow things down, no matter how much data is being sent.

\begin{itemize}
\item \textbf{Header and framing overhead.} Every TLP, regardless of payload size, must be assembled, have its header fields populated, and pass through link-layer framing (start/end control symbols, CRC) before transmission, and must be decoded and checked symmetrically at the receiver.
\item \textbf{Credit-based flow control.} A PCIe transmitter cannot send a TLP unless the receiver has already granted it enough flow-control credits -- essentially a balance that must be topped up before the next TLP can go out. On a link that is otherwise idle, the first TLP of a transaction typically has to wait out a full credit round-trip before it can be sent; posted writes and completions that follow it can then pipeline behind that initial wait. Budruk et al.~\cite{budruk2004pcie} give a detailed treatment of this credit mechanism.
\end{itemize}

When you're sending data, there are a couple of costs to consider. First, there's a fixed cost that doesn't change no matter how much data you're sending. This cost is like a fee that you have to pay every time you send something, and it doesn't depend on the size of what you're sending. Then, there's the cost of actually sending the data itself, which does depend on how much data you're sending. If you're sending a lot of data, it takes longer than if you're sending just a little bit. The time it takes to send the data is related to how many units of data, called DWORDs, you're sending. A DWORD is just a group of 4 bytes, and the time it takes to send your data is proportional to how many of these groups you have. So, if you have a lot of data, you'll have a lot of DWORDs, and it will take longer to send. This is why a connection that seems really fast when you're sending a lot of data might seem slower when you're sending just a little bit. This idea - that there's a fixed cost, plus a cost that depends on how much data you're sending - is the basis for a model that helps us understand how long it takes to send data over a connection. This model is explained in more detail in a later section, and it can help us figure out how to make our connections faster and more efficient.

\section{The AMBA AXI4 and AXI4-Stream Protocols}
\label{sec:ch3_axi}

On the fabric side of a PCIe endpoint, the \ac{AMBA} \ac{AXI4} protocol \cite{arm2021axi} provides a memory-mapped, burst-oriented interface with independent, decoupled address and data channels, and is the interface most on-chip DMA engines and memory controllers present to a bus fabric. \ac{AXI4-Stream} \cite{arm2010axistream} is a companion protocol that removes addressing entirely, retaining only a simple point-to-point, back-pressured data channel intended for continuous or packetised data movement between IP blocks. Its handshake and sideband signals, all of which are used directly by the datapath implemented in this thesis, are:

\begin{itemize}
\item \texttt{tvalid} / \texttt{tready} -- a standard two-way handshake: a beat transfers on any clock edge where both signals are asserted. Either side may assert its signal without waiting for the other -- a producer with data ready can raise \texttt{tvalid} before it sees \texttt{tready}, and vice versa -- which is what lets a downstream stage push back on an upstream one and controls the flow of data through the pipeline.
\item \texttt{tdata} / \texttt{tkeep} -- the payload of the beat and a byte-valid mask, used so that the final beat of a packet whose length is not a multiple of the bus width can mark only its genuinely valid bytes.
\item \texttt{tlast} -- asserted on the final beat of a logical packet, delimiting packet boundaries on an otherwise continuous stream.
\item \texttt{tuser} / \texttt{tid} -- two sideband fields this thesis repurposes to carry per-packet metadata through the pipeline: \texttt{tuser} holds the packet length in bytes and \texttt{tid} a unique per-packet tag. Carrying both fields through every stage means downstream logic and the latency-measurement block can read the metadata they need directly, without a separate side-channel (\autoref{sec:ch4_sideband}).
\end{itemize}

When you're working with AXI4-Stream, each handshake can be controlled separately, which makes it really useful for building multi-stage pipelines. Essentially, this means that each part of the pipeline only needs to make sure it's handling its own inputs and outputs correctly, and then everything will work smoothly from start to finish. You won't have to worry about losing or duplicating data as it moves through the pipeline. This is why, in this particular project, the data path is set up as a series of independent AXI4-Stream stages, rather than one big, complex system. This approach makes it easier to manage and understand what's going on, as each stage can be designed and tested on its own without affecting the others.

\section{Descriptor-Based DMA Operation}
\label{sec:ch3_dma}

A DMA engine such as the AMD-Xilinx AXI DMA \ac{IP} \cite{xilinx2021axidma} decouples the host (or an on-chip processor) from the actual movement of data by operating on \emph{descriptors}: small, fixed-format records that specify a source address, destination address, transfer length, and control flags for one transfer. In the simplest, non-scatter-gather mode of operation, the host writes the relevant address/length registers and then triggers the engine, typically by asserting a "run" bit or ringing a doorbell; in scatter-gather mode the engine itself walks a descriptor ring in memory, fetching each descriptor before acting on it. Either way, before the first byte of payload can move, the engine must:

\begin{enumerate}
\item Fetch the descriptor itself -- a memory or PCIe transaction in its own right, and one that pays the same round-trip latency as any other transaction on that link.
\item Parse the descriptor fields and load its internal address or length counters.
\item Arbitrate for and begin the underlying memory-mapped read or write burst.
\end{enumerate}

When it comes to PCIe TLP framing, the time it takes to process the sequence is pretty much the same, no matter how many bytes are being transferred. So, whether you're transferring one byte or one megabyte, the cost of processing the descriptor is the same. But once the transfer starts, the speed at which data is moved depends on the engine's internal datapath width and how fast it can burst data from the memory it's reading or writing to. This means the total time it takes to complete the transfer is directly related to the size of the payload and the engine's effective rate of transferring bytes per cycle. This setup, where there's a fixed cost for setting up the transfer and a variable cost that depends on the size of the transfer, is similar to how PCIe transactions work, as we discussed earlier. And that's why these two effects can really add up when you're dealing with small packets.

\section{Latency Model}
\label{sec:ch3_latency_model}

When you combine the PCIe transaction layer, discussed in section \autoref{sec:ch3_pcie}, and the DMA engine, covered in section \autoref{sec:ch3_dma}, you get the total latency for a packet of $S$ bytes. This can be broken down into two parts: a fixed latency and a proportional latency that depends on the size of the packet. So, the total latency is the sum of these two parts, which can be thought of as a fixed cost plus an additional cost that's proportional to the packet size.

\begin{equation}
L_{PCIe}(S) = T_{base} + \left\lceil \frac{S}{4} \right\rceil \cdot T_{dw}
\label{eq:pcie_latency}
\end{equation}

\begin{equation}
L_{DMA}(S) = T_{setup} + \left\lceil \frac{S}{W} \right\rceil
\label{eq:dma_latency}
\end{equation}

\begin{equation}
L_{tot}(S) = L_{PCIe}(S) + L_{DMA}(S) + L_{other}
\label{eq:total_latency}
\end{equation}

Here, $T_{base}$ is the fixed per-transaction overhead on the PCIe side -- header assembly, credit checks, and link framing -- and $T_{dw}$ is the additional delay incurred per 4-byte DWORD of payload. $T_{setup}$ is the fixed cost of processing the DMA descriptor, and $W$ is the DMA engine's datapath width in bytes per cycle. $L_{other}$ lumps together the small, residual latency contributions of the remaining pipeline stages -- the AXI-Stream adapter, an empty FIFO, and the sink. Chapters~4 and~5 implement these equations directly as finite-state machines with representative parameter values: $T_{base}=20$ cycles and $T_{dw}=1$ cycle per DWORD for the PCIe stage, roughly equivalent to a 100--200~ns round trip at a 100~MHz simulation clock, and $T_{setup}=8$ cycles with $W=8$ bytes/cycle for the DMA stage. Chapter~6 then validates the latency of the implemented RTL against these closed-form expressions using hardware measurements taken from the simulated design itself.

Two consequences of Equations~\ref{eq:pcie_latency}--\ref{eq:total_latency} motivate the rest of this thesis. First, effective per-byte efficiency,
\begin{equation}
\eta(S) = \frac{S}{L_{tot}(S)},
\label{eq:efficiency}
\end{equation}
The total latency is directly related to the size of the data being transferred, and it increases as the data size grows. When the base time, downtime, setup time, and packet size are fixed, the latency becomes a strictly increasing function of the data size. This happens because the fixed costs, such as the base time and setup time, are spread out over a larger amount of data as the data size increases. At the same time, the costs that are proportional to the data size grow linearly with it. This effect has been measured in experiments, as discussed in a previous section. Additionally, when multiple packets of data are sent separately, the total latency is the sum of the latency for each packet. However, if these packets are combined into a single, larger packet before being sent, the fixed overhead costs are only paid once. This can significantly reduce the total latency, especially when transferring large amounts of data. For instance, if several packets are coalesced into one packet, the base time and setup time are only incurred once, rather than multiple times. This reduction in overhead costs can lead to improved performance and efficiency in data transfer.

\section{Buffering, Back-Pressure, and Queueing Behaviour}
\label{sec:ch3_queueing}

When we look at how long it takes for a packet to go through a pipeline that's not being used by anything else, we use equations like the ones labeled \ref{eq:pcie_latency} to \ref{eq:total_latency}. But in real situations, we put a buffer between where the data is being made and where it's being used. This buffer helps deal with times when data is being made faster than it's being used. The old way of thinking about this, called classical queueing theory, says that as long as data isn't coming in faster than it's being used, the buffer won't get full and won't slow things down. This is like a line of people waiting for a bus - if the bus comes often enough, the line won't get too long. But if the buffer is only so big, once it gets full, it will start to slow down the data that's coming in. This is important to remember when we're talking about something like an AXI-Stream FIFO, which is a kind of buffer. The size of the buffer decides how much extra data it can handle before it starts to slow things down, not how long it takes for data to get through once it's flowing steadily. We'll come back to this idea later with some actual measurements from hardware that show the difference between these two things.
