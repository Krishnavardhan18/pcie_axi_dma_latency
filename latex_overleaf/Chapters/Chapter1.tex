\section{Background}
\label{sec:ch1_background}

When it comes to connecting high-performance devices like network cards, storage controllers, and custom hardware to a computer's processor, PCIe has become the go-to standard. This is because it allows for really fast data transfer between the device and the computer's memory. Most of these devices use something called a DMA engine to move large amounts of data back and forth, rather than relying on the computer's processor to do it. This is a good thing, because it means the computer's processor can keep doing other important tasks without getting bogged down by all the data transfer. On the other side of the connection, inside the device itself, these DMA engines are usually built using a set of standard protocols called AMBA AXI. There are a few different versions of AXI, but the one that's specifically designed for moving large amounts of data around is called AXI4-Stream. 

When data is transferred from a host to a device or vice versa, it has to cross two different protocol areas. On the PCIe side, data is packaged in something called TLP, which has a fixed-size header and is controlled by a credit-based system to prevent overload. This system also means that there's a delay while the transfer is acknowledged. On the other side, the AXI side, there's a special engine called a DMA engine that helps translate the data. This engine takes memory-mapped burst reads and writes and turns them into byte-enabled AXI4-Stream beats. But before it does that, it usually has to fetch a descriptor, which is like a set of instructions that says where the data is coming from, where it's going, and how much data there is. Both of these steps - packaging the data in TLP and fetching the descriptor - take some processing power, and this cost doesn't really change no matter how much data is being moved. This means that whether you're moving a little data or a lot, these steps still take up the same amount of resources. For example, the AMD-Xilinx AXI DMA engine or the integrated PCIe block on UltraScale+ devices are two examples of DMA engines that do this translation work. They help make sure that data gets from where it is to where it needs to go, even though the protocols on either side are different. So, in summary, transferring data between a host and a device involves crossing two protocol domains, and this process has some fixed costs that don't depend on the amount of data being transferred. These costs come from the way data is packaged and controlled on the PCIe side, and from the work that the DMA engine does on the AXI side to translate between different types of data transfers.

For large transfers (multi-kilobyte and above), this fixed cost is negligible relative to the time spent moving payload bytes, and the datapath approaches its peak link bandwidth. For small transfers, however, the same fixed cost dominates: a 64-byte packet pays essentially the same TLP-header and descriptor-setup penalty as a 4096-byte packet, so its effective throughput and per-byte latency are far worse. Such small, latency-sensitive transfers are common in practice, network packet forwarding, sensor telemetry, control-plane messages, and lock-step accelerator hand-offs all routinely move payloads well under one kilobyte, which makes the small-packet regime an important, if under-examined, corner of PCIe-AXI DMA system design.

\section{Motivation}
\label{sec:ch1_motivation}


When designing systems with AXI DMA and PCIe integrated-block IP cores, it's tough to get a clear picture of how all the components work together. The vendor documentation usually covers the basics, like how the different parts function, what the register maps look like, and the maximum bandwidth. But it often falls short when it comes to detailing how the entire pipeline - from PCIe to DMA to AXI-Stream - performs with different packet sizes. And rarely do you get a detailed, cycle-by-cycle breakdown of where the latency is coming from, especially for small transfers. This leaves system architects in a tricky spot, having to either overestimate the buffering needs, make educated guesses about the achievable throughput for small packets, or wait until the silicon or FPGA is up and running to discover the actual performance penalties. Previous research on PCIe performance, like the work done by Neugebauer et al., has shown that the performance of small transfers is mostly limited by the overhead of each descriptor and Transaction Layer Packet (TLP), rather than the raw bandwidth of the link. However, this research focused on characterizing the performance of complete systems, rather than providing a detailed, open, and adaptable model that designers can use to simulate and optimize their own systems. In essence, the current state of affairs leaves a lot to be desired when it comes to understanding and optimizing the performance of AXI DMA and PCIe integrated-block IP cores. But by providing more detailed, adaptable models and tools, designers could gain the insights they need to create better, more efficient systems, and unlock the full potential of these technologies.

\section{Problem Statement}
\label{sec:ch1_problem}


Given a PCIe-AXI DMA streaming datapath composed of a PCIe transaction layer, a descriptor-driven DMA engine, an AXI-Stream buffering stage, and a consumer, this thesis addresses the following problem: \emph{quantify the end-to-end latency and effective throughput of the datapath as a function of packet size, decompose that latency into its PCIe, DMA, and buffering contributions, and design an RTL-level optimisation that measurably improves small-packet efficiency without modifying the underlying PCIe or AXI protocols.}

This problem is broken down into four smaller parts, which we'll look at in more detail later on.
\begin{enumerate}
\item \textbf{Modeling.} Derive closed-form, packet-size-dependent latency expressions for the PCIe transaction layer and the DMA engine, grounded in the fixed-overhead-plus-linear-transfer structure documented for real TLP framing and descriptor processing (\autoref{Chapter3}).
\item \textbf{Implementation.} Realise these models, together with an AXI-Stream FIFO, a batching unit, and a hardware latency-measurement block, as synthesisable SystemVerilog RTL that can be simulated cycle-accurately (\autoref{Chapter4}, \autoref{Chapter5}).
* **Measurement**: Create a test system that checks itself and sends different types of packets through the RTL pipeline. This system measures how long it takes for each packet to go through, and it does this directly in the hardware, without using any software to help it (\autoref{Chapter6}).
\item \textbf{Optimisation and evaluation.} Implement a small-packet batching unit, and quantify its latency and efficiency benefit against the un-batched baseline, together with a study of how AXI-Stream FIFO depth affects buffering headroom under a rate-limited consumer (\autoref{Chapter7}).
\end{enumerate}
